Документ обновлён 28 октября 2026 года. Ниже зафиксированы результаты проверок,
выполненных 26–27 октября. Это отчёт о проверенном состоянии, а не мониторинг
текущей доступности демонстрационного окружения.

- `npm run typecheck`: проверка TypeScript.
- `npm run smoke`: Next.js production server с тестовым HTTP API.
  Проверены SSR товара, свежие данные при следующем запросе, пустой поиск,
  отдельное сообщение ошибки API и заголовок `no-store`.
- Полный набор backend-тестов в Docker с PostgreSQL: **34 passed**, без пропусков.
  Проверены обработчики бота, авторизация, валидация, API и очередь обновлений.
- Workflow `Checks` в GitHub Actions успешно завершён для коммита `a98c5b9`.

Автоматические тесты Telegram используют тестовую HTTP-сессию. Проверка настоящего
бота выполнена отдельно и описана ниже.

## Проверка работающего приложения

- Проект собран и запущен через Docker Compose с PostgreSQL и MinIO.
- Зарегистрирован Telegram webhook через публичный HTTPS-туннель.
- Администратор отправил `/create`, затем фото с названием в подписи одним сообщением.
  Бот подтвердил добавление; товар и изображение появились в каталоге.
- Каталог проверен в обычном браузере и Telegram Desktop Mini App.
- Ранее добавленные товары сохранились после остановки и последующего запуска окружения.
- Одновременно запущены две реплики каждого сервиса `api`, `bot`, `web`;
  все шесть контейнеров имели статус `healthy`.

## Проверка работы при остановке реплик

При работающих двух репликах каждого сервиса выполнена команда:

```powershell
docker stop telegram-catalog-api-1 telegram-catalog-bot-1 telegram-catalog-web-1
docker compose ps -a
```

Первые реплики перешли в состояние `Exited`, вторые оставались `healthy`.
При остановленных первых репликах через Telegram добавлен новый товар
«Проверка одной реплики». Бот подтвердил добавление, товар с изображением
появился в каталоге браузера.

После проверки остановленные контейнеры запущены снова:

```powershell
docker start telegram-catalog-api-1 telegram-catalog-bot-1 telegram-catalog-web-1
docker compose ps
```

Все шесть реплик приложения вернулись в состояние `healthy`. После восстановления
каталог с новым товаром также проверен в Telegram Desktop Mini App.

Этот сценарий подтверждает обработку новых операций оставшимися репликами после
штатной остановки одной реплики каждого сервиса. Он не проверяет аварийное завершение
процесса посреди задания, отсутствие кратковременных ошибок при переключении,
отказ всего компьютера или отказ хранилищ.

## Воспроизведение проверок

Подготовьте окружение по [README](../README.md). Для автоматических тестов:

```powershell
docker compose --profile test build tests
docker compose --profile test run --rm tests
```

Для проверки нескольких экземпляров:

```powershell
docker compose up -d --scale api=2 --scale bot=2 --scale web=2
docker compose ps
```

После появления статуса `healthy` у шести реплик настройте HTTPS и webhook по README.
Повторите остановку первых реплик, добавление нового товара и открытие каталога
в браузере и Mini App. Затем восстановите остановленные контейнеры.
Имена контейнеров в командах выше относятся к проекту `telegram-catalog`;
при другом имени Compose-проекта используйте имена из `docker compose ps`.

## Непроверенные сценарии и ограничения

- Ручная проверка Mini App на физическом мобильном устройстве не зафиксирована.
- Ручная проверка добавления товара с отдельного неадминистраторского аккаунта
  не зафиксирована; ограничения доступа проверяются автоматическими тестами.
- Нагрузочные испытания и аварийное завершение worker во время обработки
  настоящего Telegram-сообщения не проводились.
- PostgreSQL, MinIO и Nginx представлены одним экземпляром. Отказоустойчивость
  всей инфраструктуры и восстановление из резервных копий не проверялись.
- Постоянный серверный деплой не настроен. Проверенное демо использовало временный
  HTTPS-туннель к локальному компьютеру; его доступность зависит от этого окружения.
